# Architecture — Sudoku Premium Edition

## 1. Architecture principles

1. Correct puzzle logic is isolated from UI and ads.
2. Offline play is the default path; no account or connectivity is required.
3. Build incrementally inside Google AI Studio's supported single-activity, single-module native Android structure.
4. Treat persistence and ad SDKs as adapters around the game domain, not as part of the puzzle rules.
5. Online ranking is a separate trust boundary: the backend, not the client, decides whether a submitted score is valid.

## 3. Domain model

### SudokuPuzzle
- `puzzleId`: stable local ID.
- `seed`: deterministic generator seed where applicable.
- `difficulty`: Easy / Medium / Hard / Expert.
- `givens`: 81 values with zero representing blank.
- `solution`: 81 validated values, retained locally as needed for hinting and completion checks.
- `challengeDateKey`: optional ISO date key for a daily challenge.
- `generatorVersion`: identifies rules/seeding version to preserve deterministic challenges across app updates.

### GameState
- puzzle reference / puzzle ID.
- `entries`: 81 values (0 means empty).
- `notes`: candidate set or bitmask for each cell.
- selected cell (UI state can be transient).
- elapsed duration and whether timer is paused.
- mistake count, hints used, undo/redo history.
- completion flag and completion timestamp.

### Game event rules
- Given cells are immutable.
- A cell entry is accepted only for a value 1–9 or cleared to empty.
- Notes never count as placed values.
- A hint modifies a cell only through the same validated domain action used for normal entries.
- Completion is idempotent; recording a result twice must not add duplicate statistics or achievements.
- Undo/redo must not undo the initial givens.

## 4. Generator and solver strategy

1. Construct a completed valid board using randomized backtracking with constraint tracking for row, column, and 3×3 box.
2. Copy the solved board, then remove candidate clues in a randomized order.
3. After each removal, run a solution counter that stops at two. Keep the removal only if exactly one solution remains.
4. Rate the puzzle using solver effort / techniques and calibrated bands for the requested difficulty. Clue count may be a helpful heuristic but is not a sufficient difficulty metric by itself.
5. Apply a maximum attempt / time budget. If target difficulty is not reached, use a cached validated puzzle or retry safely; never block the UI thread.
6. Validate the final puzzle and solution before returning it to the UI.
7. Run generation off the main thread. Show a lightweight loading state only if generation is not effectively immediate.

### Required invariants
- Exactly 81 cells.
- Solution contains digits 1–9 exactly once in each row, column, and 3×3 box.
- Every given equals the corresponding solution cell.
- Solver counts exactly one valid solution (stop once count reaches two).
- User-facing board remains consistent with original givens.
- Any hint refers to the current puzzle's validated solution.

## 5. Daily challenge identity

- Use a fixed date key, recommended `YYYY-MM-DD` in UTC.
- Generate from a deterministic seeded pseudorandom algorithm whose behavior is stable across app restarts and platforms for a specific `generatorVersion`.
- Include the generator version in the challenge ID, e.g. `daily-v1-YYYY-MM-DD`.
- Cache the puzzle locally the first time it is used that day.
- Do not claim cross-version or server-wide competitive fairness until the backend defines the canonical puzzle, seed, scoring and validation rules.

A deterministic local seed is convenient for offline use, but a modified client can cheat; it is not a security measure.

## 6. Persistence

Recommended storage split:
- Room: puzzle saves, game history, daily challenge completions, aggregate statistics, achievements.
- DataStore: theme, sound/haptics, mistake highlighting, timer preferences and UI settings.

If AI Studio has difficulty configuring Room in its current environment, ship an isolated repository interface and a simpler durable local adapter first, then migrate without changing domain APIs. Do not keep the only game save in a ViewModel or process memory.

Write saves after meaningful board actions with safe throttling/debouncing, on pause/background, and on completion. Persistence must not block taps or puzzle validation.

## 7. Navigation / screens

- Home: Continue, New Game, difficulty, Daily Challenge, Statistics, Achievements, Settings.
- New Game: select difficulty, then start valid puzzle.
- Game: grid, selected-cell state, digit pad, notes, erase, undo/redo, hint, timer, pause, settings shortcut.
- Completion: duration, difficulty, mistakes/hints, play again, home.
- Daily: current challenge, rules/date key, completion state, personal best; clearly label rankings as unavailable until backend exists.
- Statistics: total games, completion rate, time per difficulty, streaks.
- Achievements: unlocked and in-progress cards.
- Settings: themes, interaction preferences, accessibility, privacy/about.

## 8. Ads adapter boundary

UI requests an ad-related action through `AdsController`; UI must not directly manage SDK objects or callbacks. The controller should expose safe states: unavailable/loading/ready/showing/earned/closed/failed. Reward callbacks must be idempotent. The game must continue if ad SDK initialization fails, no fill occurs, consent is unavailable, or network is offline.

Keep ad SDK initialization and ad placements disabled behind a feature/config flag until puzzle gameplay and core QA are stable.

## 9. Online extension after export

Backend responsibilities for a real leaderboard:
- Publish a canonical daily challenge ID and puzzle/score rules.
- Validate challenge version, completion and time bounds.
- Reject malformed, duplicate, stale and obviously impossible submissions.
- Apply rate limits and idempotency keys.
- Store public profile identifiers separately from sensitive account information.
- Return ranked records with privacy-safe display names.

Client responsibilities:
- Queue a pending result when offline.
- Upload through an authenticated API when available.
- Show Pending / Submitted / Rejected states honestly.
- Never claim that client-side validation proves a score is fair.
